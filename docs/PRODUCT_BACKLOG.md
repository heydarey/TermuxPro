# TermuxPro 产品迭代 Backlog

本文件记录当前可验证事实，不把首版发布视为产品完成。每轮迭代关闭最高优先级纵向切片后继续审计。
产品边界：Termux 原本已经具备的终端基础能力只做兼容守护，不作为主要研究和重造方向；TermuxPro 的
主要价值应落在远程工作区、AI CLI、tmux/Git 可视化管理、自定义快捷指令、移动端交互和工具箱等增值
服务上。任何增值改动必须确保原始终端能力不受影响，失败时回退到原始终端仍可用。
用户反馈明确要求：原本 Termux 已有的功能不再进入研发研究队列，TermuxPro 只打磨增值服务，同时把
原始能力纳入兼容回归，防止增值层污染基础终端体验。
选题门禁：新增研发切片必须先证明属于 TermuxPro 增值服务；若只是 Termux 原有基础能力，只能进入
兼容回归清单，不能作为主线需求继续研究或重做。评审时必须写明分类：远程工作区、AI CLI、tmux/Git
可视化、自定义快捷指令、移动端工作流效率、上下文工具箱，或原始能力兼容守护；只有前六类进入主线
迭代，最后一类只用于证明 TermuxPro 没有破坏官方 Termux 原有能力。
产品负责人在拆需求时必须先回答“这是不是 TermuxPro 增值层”。如果只是原始终端、PTY、包管理、本地
shell、基础会话、基础快捷键或基础文件能力，不进入产品主线，只补不破坏回归、上游同步风险和安全回退。
真正进入主线的工作应围绕手机 SSH 远程开发、Claude/Codex CLI、tmux/Git 管理、自定义快捷指令和低频
工具箱，把用户从记命令、找入口、判断风险和恢复上下文的负担中解放出来。
负责人日常迭代不采用被动工单模式。每轮必须主动找出至少一个“用户没有明确提出但影响真实使用”的问题，
例如入口不直观、信息层级过重、下一步不明确、危险动作过强、通知/分支/Release 噪声、测试门禁反复失败
或仓库说明过期；先记录事实证据，再按价值、风险和成本自主排期，不等待用户逐条补漏。
用户反馈不是唯一输入源。负责人必须在日常巡检中把“找不到、看不懂、不敢点、点错不可恢复、流程噪声、
重复劳动、规则过期、门禁失真”视为主动需求来源；发现后允许直接调整产品、交互、流程和自动化，不把
旧文档或已完成状态当成固定结论。
执行要求：每轮必须留下至少 3 个主动发现候选观察，其中至少 1 个来自负责人走查而非用户反馈；候选项
需要记录证据、影响旅程、增值服务准入分类、优先级、推进/暂缓理由和下一动作。没有主动发现记录时，
产品、UI/UX、QA 闭环不算完成。

### 已完成纵向切片：Git 工作台基础闭环（0.3.0）

- 用户与场景：开发者进入远程项目后，需要先确认当前仓库、分支和工作树状态，再查看分支、切换分支、

- 非目标：首轮不做云同步、跨设备共享、公共指令市场，也不允许指令绕过 SSH 主机身份与工作区可信状态。
