# 主动产品发现机制治理记录（2026-09-09）

## 背景

用户指出：TermuxPro 的产品负责人不能只等用户逐项提出问题；日常迭代规程中发现不合理的地方，应在
红线内自行优化调整。本次治理把该反馈升级为流程缺陷，而不是普通功能需求。

## 本轮主动发现候选

| 候选观察 | 来源 | 影响旅程 | 准入分类 | 优先级 | 处理结论 |
|---|---|---|---|---|---|
| 每轮“主动发现”已有原则，但缺少可检查产物，容易退化成只响应用户工单。 | 用户反馈 + 规则审计 | 全部日常迭代 | 移动端工作流效率 / 发布交付体验 | P0 | 已硬化为每轮至少 3 个候选观察、至少 1 个主动走查来源，并写入 AGENTS、Codex/Claude skill、TEAM_WORKFLOW、UX_QUALITY 和 Backlog。 |
| README 仍主要描述一次性功能分支，容易诱导维护者继续为小改动开大量分支。 | 负责人主动审计 | GitHub 仓库维护、协作接手 | 发布交付体验 | P1 | 已改为长期 `dev_dailyIteration` 默认承载普通日常维护；独立分支只用于发布列车、hotfix、高风险隔离或协作审查。 |
| 发布描述容易被理解为“通过验收就马上发候选”，缺少 HOLD 口径，可能继续制造 Release 噪声。 | 负责人主动审计 | 版本下载、用户通知、发布节奏 | 发布交付体验 | P1 | 已在 README 强调持续迭代不等于按提交发包，每周发布评审可为 READY/HOLD/RELEASED，未达价值或质量标准不发包。 |
